# What is inside the jsonb

Generated by `scripts/jev-jsonb-census.mjs` on 2026-09-21. Re-run it; do not hand-edit.

The column-level catalogue found jsonb to be the largest pool of free text in the database,
~215M tokens across 252 columns, more than every plain text column combined, and then only
ever treated it as something to read. A jsonb column is not one field, it is a schema nobody
declared. This says what is in them.

## Summary

- **215 jsonb columns** sampled (tables with >= 100 rows).
- **135** hold objects with readable top-level keys.
- **80** hold no object at the top level (arrays or scalars), so there are no keys to promote.
- **220 keys are enums in hiding**: short strings, few distinct values. These want promoting to real columns, not classifying. A model is the wrong tool.
- **58 keys hold prose**: a typed judgement could read them.

**A threshold has to be relative to its sample.** The first version of this script called a
key an enum when it had 25 or fewer distinct values, tested against a 50-row sample where
distinct can never exceed 50. Everything looked like an enum. Distinctness is now a ratio and
needs at least 30 sampled rows before it says anything.

**Sampling.** Up to 200 rows per column, drawn with `TABLESAMPLE SYSTEM` on any table
over 20,000 rows. The first run used an unordered `LIMIT`, which returns the first pages of
the heap: on a table written in ingest phases that is ONE batch. It reported
`gs_relationships.properties.receipt_type` as having a single distinct value across 200 rows.
It has several. A cardinality read off the first page of a phase-written table is fiction.

Rows marked `fallback-unordered` in the JSON are small or sparse tables where TABLESAMPLE
returned nothing and the unordered form was used instead; treat their cardinalities with the
same suspicion.
